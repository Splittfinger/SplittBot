Status: the development checkpoint and local acceptance pass are complete. The supervised personal-use beta can proceed for existing email access; this is **not** public-release or week-long reliability sign-off.

## Changes from this readiness pass

- Disable every configured app outside a Bot's grants, including explicitly enabled apps missing from catalog discovery. The default-disabled policy alone does not override an app's explicit enablement.
- Set runtime write-review policies for custom MCP and connected apps. Override inherited automatic approvals at app, tool, and app-account levels; retain stricter prompts and disabled tools. App approval reviewers are explicitly human. Read-only Bots also disable app tools advertised as destructive.
- Make diagnostic logs owner-only, including pre-existing files, and create new log directories privately.
- Add regression coverage for these boundaries and an unauthenticated bundled-runtime protocol check. The protocol check creates only an ephemeral thread in a fresh temporary profile; it never borrows credentials or starts a model/tool turn.
- Make desktop tests choose their viewport and media preferences explicitly. The first remote run exposed assumptions about the hosted Mac's display size and reduced-transparency setting. Compact, high-contrast, reduced-motion, and reduced-transparency checks remain enabled; production accessibility behavior was not changed.

The OpenAI Docs skill informed the policy changes, using the [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) and types generated by the bundled `codex-cli 0.153.4`. The runtime accepted the app/MCP policy and confirmed the read-only sandbox and human reviewer. This verifies configuration compatibility, not adversarial enforcement of every provider tool.

## Gates still open

1. **Local Mac permissions.** A fresh check reported Accessibility and Screen Recording denied; the local iMessage status check was blocked. Earlier August passes are historical, not current evidence. The iMessage skill requires stopping at denied status; no database copying, privacy bypass, or send was attempted. The user must enable Accessibility, Screen Recording, and (for Messages) Full Disk Access for the exact installed SplittBot bundle, then quit/reopen and recheck. Local ad-hoc signing is not a substitute for a stable Developer ID release identity.
2. **Two real Outlook identities.** There are currently no custom connector-account identities in the local desk. Current built-in Outlook access is granted to Email Cleanup. SplittBot's implemented two-account routing applies to custom HTTP MCP sources, not a per-Bot identity picker for built-in Outlook. Need the second mailbox identifier, an appropriate account-capable connector, and the user's Microsoft authorization. No useful account was revoked to manufacture a test pass.
3. **Real sleep/wake and connection expiry.** Deterministic restart, cancellation, recovery, and catch-up coverage passed. A physical sleep/wake test and a deliberate disposable-account revoke/reconnect still require supervised observation. Do not interrupt the user's Mac or revoke production credentials without coordination.
4. **One-week pilot.** Not complete and not silently scheduled. Await the user's choice of daily run time or manual runs. Existing Bots and schedules were not expanded or duplicated during acceptance.
5. **Public distribution.** No signing identities were available on this Mac and the repository secret-name listing was empty. Developer ID/notarization credentials, provisioned runtime components for both architectures, runtime redistribution review, and a clean-Mac install/update acceptance pass remain release gates. No notarization or public binary release was attempted.

## Seven-day pilot checklist

Use Email Cleanup's existing account, with Atlas as a shared-result reviewer. Begin with read-only triage; writes still need fresh human approval. Run only while the Mac is awake and SplittBot is running.

For each day record: scheduled and actual start; completion/failure; account used (locally only); count of actionable findings and retained Actions; Atlas review present; pending approvals; duplicate or missing items; and recovery after interruption. Record failures even if a retry later succeeds. Keep mailbox contents and account identifiers out of GitHub.

Acceptance requires seven observed daily runs, no wrong-account calls, no unauthorized writes, no lost Actions, and no silent failures. Intentionally test one restart and one coordinated sleep/wake, then verify the existing Action remains actionable. Resolve or snooze a real item only when the user actually decides to do so. An empty sample is valid but does not replace a positive-content test.

## Remaining security limitations

Runtime policies still depend on provider tool annotations and supported approval flows. Readable-root and command-template profile fields are not complete OS-enforced allowlists; network-enabled commands and untrusted third-party tools need a stronger authorization design before broader distribution. This pass does not claim hostile-tenant isolation, encrypted local storage, or exhaustive prompt-injection resistance. Stronger confinement and adversarial approval tests remain a separate release gate.

## Reproduce the checks

```bash
npm run typecheck
npm test
npm run test:e2e
npm run test:packaged
npm run test:runtime-policy -- /absolute/path/to/SplittBot.app/Contents/Resources/runtime/darwin-arm64/codex
```

Packaged tests use isolated data. Do not package over a running installed bundle: stage a separate build, verify it, quit the idle installed app, preserve the old bundle, then replace it. Keep live acceptance distinct from fixture results.
